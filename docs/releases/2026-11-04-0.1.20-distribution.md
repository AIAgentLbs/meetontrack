# Public MeetOnTrack 0.1.20 distribution acceptance

Date: 2026-11-04. Downloadable technical beta, not a stable/hardware-certified
release. Owner approved building, publishing for Mac and Windows, updating the
website and installing on the owner's Mac on 2026-11-04 ("0.1.20 тоже"). Same
process as [0.1.19](2026-11-04-0.1.19-distribution.md); this record lists what
differs.

Contents: MEETONTRACK-120 (meeting reports on Windows: the PDF is printed by
Chrome or Edge; on macOS Chrome, then Edge or Chromium; a report that cannot
become a PDF still goes out by email and Telegram as one HTML file with a
note, and the PDF is retried) and MEETONTRACK-119 (the remaining edge cases of
carrying speaker corrections to the final transcript), with their review
fixes. Branch `feat/one-app` (0.1.21) is not included.

## Immutable package identity

Both packages embed application revision `aedbff8`. `git diff
v0.1.19..aedbff8 -- capture/ windows/` is empty.

Mac: the Swift binary, Sparkle and LocalVQE were reused from the published
0.1.19 archive and assembled as 0.1.20 (build 451). Without its ad-hoc
signature the binary is byte-identical to 0.1.19's; LocalVQE files are
byte-identical. Compared with 0.1.19 the manifest adds the two new test files
(3,903 files); besides the Info.plist, the re-signed binary and 6 changed web
files, only three Python script files differ, by the temporary build path in
their shebang/RECORD lines (as in every build).

Windows: the recorder was rebuilt from `windows/` in
[windows-candidate run 41865457069](https://github.com/AIAgentLbs/meetontrack/actions/runs/41865457069)
at `aedbff8` with version 0.1.20 (core and live tests, report PDF printed with
Chrome and with Edge, `managed.zip` SHA-256 `c5a8a02c...`, its own candidate
accepted). The release archive was composed locally from that `managed.zip`
with `package_candidate.py`. Against 0.1.19, `python/` is identical; in
`capture/` only the 5 rebuilt recorder files (`MeetingCopilotCapture.exe/.dll/.pdb`,
`Amanu.Core.dll/.pdb`) differ, the .NET runtime files are identical. Against
the CI-composed candidate, `capture/` and `python/` are identical; root text
files differ by line endings and `web/_vendor` by the interpreter that built it,
as for 0.1.19.

Commits: pins `31dcd25`; Windows notes and `windows-v0.1.20` tag/target
`2b6bcd39fd1253c71927adb97dd72cc6205997fa`; Mac notes and `v0.1.20` tag/target

## Known gaps

- The Windows machine still runs 0.1.13.
- MEETONTRACK-121 (two rarer speaker-carry cases), MEETONTRACK-122 (a restart
  between the email and the Telegram send can resend the email),
  MEETONTRACK-118 (3-day final-transcript window), MEETONTRACK-106 and
  MEETONTRACK-108 remain.
- When the first browser found fails to print, the next one is not tried; the
  report goes out as HTML and the PDF is retried (Codex P3, stated in the notes).
- `swift-build` CI did not run at `aedbff8` or on the release commits because of
  the macOS runner shortage; re-run when runners are available.
- This Mac's GitHub token lacks `workflow` scope; the pin commit touching the
  workflow was pushed from the devserver (from a bundle of the same commits).

## Explicit limits

No clean Mac and no audio hardware tests. The Windows report PDF was printed
with Chrome and Edge on the CI runner from a fixture meeting, not from a real
call; the HTML fallback and speaker carry-over were checked by unit and UI
tests. Mac is ad-hoc signed and not notarized; Windows is unsigned. No
automatic installer is enabled. Never restart an active recording to update.
